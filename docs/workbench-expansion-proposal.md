# Forma 工作台扩展：知识库、技能库与完整工作闭环

日期：2026-11-02。状态：研究与产品设计建议，尚未实现的新能力不属于当前 Alpha 的已交付功能。

本文基于本地初版代码与公开项目文档。用户明确要求：知识库可通过指定目录或上传文件使用；内置 LLM Wiki 能力；技能支持手写、AI 辅助创建和预置选择；整体成为丰富的个人工作台。

用户已确认参考项目为 [nashsu/llm_wiki](https://github.com/nashsu/llm_wiki)。已核对其公开 README、MCP 说明、package.json 与许可证；本轮属于文档和接口层研究，尚未克隆审计核心源码或进行集成联调。具体接入建议见第 11 节。

## 1. 产品判断

当前 Alpha 已具备 Agent 与团队配置、模型连接、本地任务目录、Leader 对话、阶段执行和基础文件工具，但主要解决“组织一次工作”。下一阶段要补齐长期资料、工作方法、可执行工具和可复用成果。

建议定义的闭环：

**收集资料 → 形成知识 → 选择技能 → 团队执行 → 验收成果 → 将有效知识和方法沉淀下来。**

| 对象 | 用户需要理解的含义 | 主要生命周期 |
| --- | --- | --- |
| 知识库 | 工作所依据的资料和有来源的结论 | 接入、整理、查询、更新、归档 |
| 技能 | 完成某类工作的步骤与交付规则 | 创建、试运行、启用、改进、版本更新 |
| 工具 | 可以实际执行的操作 | 连接、授权、调用、断开 |
| Agent | 使用上述能力承担职责的个人助手 | 创建、配置、独立使用或加入团队 |
| 团队 | 用户组织的分工与协调关系 | 组建、执行、调整、复用 |
| 项目空间 | 长期目标下的任务、资料与约定 | 创建、积累、检索、备份、归档 |
| 任务工作区 | 一次持续工作的上下文和产物 | 开始、多轮对话、交付、回看 |
| 记忆 | 用户希望长期保留的偏好、规则与经验 | 提议、确认、附加、修改、删除 |

这些对象应关联，但不合并为一个“万能提示词”字段。

## 3. 知识库：用户只需选目录或添加资料

### 3.1 三种接入方式

1. **关联已有目录**：选择研究资料、项目文档或笔记文件夹。默认只读关联原文件，记录路径、来源版本和排除规则；不移动文件，也不在原目录中擅自创建 Wiki。
2. **上传/拖入文件**：复制进 Forma 管理的资料区，记录文件名、导入时间、内容哈希和来源。
3. **连接现有知识服务**：后续通过 MCP 或专用适配接入已有服务，不强制把远程数据全部复制到本机。

新增知识库向导只显示：名称、资料来源、希望整理的主题、使用的整理模型。索引、切片和检索参数放在高级设置中。支持“只建立检索”与“同时整理成 Wiki”，避免首次导入就必须等待大量模型调用。

### 3.2 知识库页面

建议包含“概览、资料、Wiki、问答、更新记录”五个页签。

- 概览：资料规模、处理进度、最近更新、需要处理的问题。
- 资料：目录树、文件预览、解析状态、最后同步时间、关联 Wiki 页面。
- Wiki：主题页、概念页、来源摘要、交叉链接、引用和修订历史。
- 问答：仅基于所选知识库回答，能够打开引用对应的原文位置。
- 更新记录：导入、更改、整理建议、采纳/拒绝和回退记录。

关系图可以后续提供，默认浏览方式仍是目录、检索和页面阅读。

### 3.3 推荐的数据流程

**接入 → 识别变更 → 本地解析 → 来源定位 → 检索索引 → Wiki 更新草稿 → 采纳/自动应用 → 后续查询。**

源文件、抽取文本、检索缓存和 Wiki 页面分别保存：

```text
knowledge/<library-id>/
  library.json          # 来源映射与知识库设置
  sources/              # 用户上传的托管副本；关联目录仍保留在原位置
  extracted/            # 可重新生成的解析文本与页码/段落映射
  wiki/                 # 可阅读、编辑、导出的 Markdown 页面
  proposals/            # 待确认的 Wiki 更新
  revisions/            # 页面历史与来源版本记录
  index.sqlite          # 元数据、检索索引与后台任务状态
```

元数据中区分“可重建缓存”和“不可丢失的用户数据”。批注、人工修订、采纳记录、来源映射与权限不能只保存在会被清空的检索缓存里。

### 3.4 Wiki 的实际行为

- 一份新增资料可以更新已有主题，而不是永远新增一张孤立摘要卡。
- 每个重要结论关联具体来源和版本；生成结论与用户人工备注明确区分。
- 不一致内容标为“冲突候选”，显示双方依据，不让模型擅自宣布其中一方为事实。
- 对人工编辑过的页面生成更新差异，保留人工内容及历史版本。
- 整理任务失败只影响当前批次，不损坏已可用的知识库。
- 查询后的有用结论可选择“沉淀为 Wiki”，默认先产生更新草稿。
- 用户可按知识库开启自动整理，并设置处理范围和费用上限；首轮不默认大规模自动重写。

### 3.5 同步与删除必须明确

目录同步使用文件指纹、变更队列、合并重复事件与启动后的补扫。区分“文件暂时不可达”和“确定删除”，避免移动硬盘断开时删掉整库索引。

修改原文件后，标记受影响页面待刷新，再更新对应部分。删除/解除关联后，停止当前检索，并标记依赖结论过期；历史任务保留当时的引用版本。若用户要求彻底删除知识，还应清除相关托管副本、索引、派生内容及历史副本，而不只是隐藏列表项。

“解除目录关联”不删除原文件；“删除托管文件”只处理 Forma 管理的副本。两种操作在界面上分别命名。

### 3.6 格式与检索路线

第一批建议支持 Markdown、TXT、文本型 PDF、DOCX 与 CSV。扫描 PDF、图片 OCR、复杂表格、PPTX、音频转录按独立解析能力逐步加入，明确显示缺少依赖或解析失败。

本地抽取优先，模型用于知识整理和回答。文档解析在独立工作进程执行，防止大文件卡住桌面窗口。MarkItDown 可评估为扩展解析器，但其 Python 与附加依赖需要纳入 Windows/macOS 安装包验证，不把命令行环境要求直接推给普通用户。

检索同时覆盖原文和 Wiki。第一阶段支持关键词、文件名、标题和目录检索；语义向量检索为可选增强，可使用用户配置的本地或云端嵌入模型。文本生成模型不自动视作嵌入模型。

中文检索必须单独测试分词、两字词和混合中英文。SQLite trigram 的全文查询对不足三个 Unicode 字符的子串有限制，不能把默认英文检索效果当作中文可用性。来源：[FTS5 trigram 说明](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。

引用最小结构建议包含 sourceId、sourceVersion、文件名、页码/标题/段落锚点和证据片段。界面引用必须由实际检索结果映射生成，不能只相信模型写出的文件名或页码。

## 4. 技能仓库：完整支持三种来源

### 4.1 自己编写

双编辑入口：

- 表单：名称、适用场景、输入、执行步骤、输出要求、所需工具、例子。
- 源码：直接编辑标准 SKILL.md 与其附带文件。

两者使用同一份技能定义。保存草稿、检查格式、试运行、启用、导出分别有明确状态。用户可以复制预置技能形成自己的版本。

### 4.2 描述需求，由 AI 帮助编写

建议流程：描述目标 → 补齐必要输入与输出 → 生成草稿 → 使用样例试跑 → 展示结果与问题 → 修改 → 保存启用。

例如用户描述：“每次读取会议记录，提炼决定、负责人、截止时间和未解决问题。”系统生成工作规则与输出模板，并用一段用户选择的示例验证。

AI 生成不是质量认证。优先检查结构、引用、输出格式与必要步骤；模型评审作为补充。脚本型技能需要明确依赖与运行方式，不能在创建时直接执行任意生成代码。

AI 创建使用用户在模型中心选择的模型，不要求额外注册或绑定固定服务商。试运行显示使用的资料和可能发生的真实调用。

### 4.3 常用技能随应用预置，用户选择使用

建议先预置约 12 个由 Forma 维护的技能包：

| 技能 | 面向的工作 | 依赖 |
| --- | --- | --- |
| 基于资料回答 | 依据已选资料回答并给出处 | 知识检索 |
| 跨文档对比 | 比较差异、矛盾与共同结论 | 文件解析、引用 |
| 研究报告 | 整理问题、证据与结论 | 知识检索；联网研究另需搜索工具 |
| 写作与改稿 | 按目标和风格生成、修订稿件 | 文本模型 |
| 会议纪要 | 提取决定、责任人与行动项 | 文本资料；音频另需转录 |
| 需求拆解 | 把需求转成明确任务与验收条件 | 文本模型 |
| 代码审阅 | 分析代码与变更并提出建议 | 代码文件访问或成熟 Agent |
| 测试设计 | 形成测试用例、边界与验证步骤 | 文本/代码；实际运行另需执行能力 |
| CSV 整理 | 清理、对比和解释结构化数据 | CSV 解析与受控数据工具 |
| 表格分析 | 汇总指标、检查异常并解释 | 表格读取和计算工具 |
| 项目复盘 | 提炼有效方法与后续行动 | 任务记录 |
| 知识整理 | 生成 Wiki 更新建议与来源关联 | 知识库服务 |

预置表示已随包提供，不代表全部默认启用。缺少工具时显示“需要配置”，不让技能卡片宣称已能完成任务。

### 4.4 文件与版本

采用标准的 SKILL.md、references、assets、scripts 结构。版本、依赖检查结果、测试样例、安装来源、内容哈希和用户授权记录由 Forma 单独管理；不把平台自定义字段冒充通用规范。

建议区分技能内容版本、用户变量配置和运行记录。正在运行的任务固定技能版本，更新后只影响新任务。预置技能升级保留用户修改，通过复制/分支和差异查看处理冲突。

第一阶段优先可移植的指令与模板型技能；脚本按受控工具能力执行。后续支持本地目录、ZIP 或固定仓库版本导入，再考虑在线技能市场。用户数据、密钥和业务样例不随技能导出。

### 4.5 使用方式

- 为 Agent 绑定默认技能集合。
- 为团队配置可用技能，并允许成员有各自范围。
- 在当前任务临时选择技能，或用 `/技能名` 显式调用。
- 对允许自动使用的技能，让 Leader 按任务需要选用，记录实际激活的版本。
- 只向模型提供适用技能目录，选中后再加载正文，资源按需读取。

安装、启用、允许自动选择、获得工具权限是不同状态。技能内容不能自行提升权限；`allowed-tools` 等字段不能直接变成宿主授权。

### 4.6 成熟 Agent 兼容

不假定一个技能文件能让所有执行器表现一致。至少记录三类能力：

1. 指令与模板：通过任务上下文注入的基本兼容。
2. 原生技能发现：经版本验证后放入任务专属的技能目录。
3. 工具/脚本执行：要求对应执行器与权限机制真正支持。

用户的全局 Codex/Claude Code 配置默认不被重写。知识查询和工具调用优先通过任务专属适配或 MCP 暴露，避免把整个知识库复制进每位成员的目录。

## 5. 还应补齐的工作台能力

| 优先级 | 能力 | 解决的问题 | 首次可交付范围 |
| --- | --- | --- | --- |
| P0 | 工具与连接中心 | 技能缺少可实际执行的动作 | 内置工具统一登记、MCP 连接、依赖状态、作用范围与错误提示 |
| P0 | 文档与资料收件箱 | 文件只能粘贴文本，收集入口太弱 | 拖入文件、目录关联、解析队列、粘贴网页链接 |
| P0 | 更完整的任务运行 | 长任务进展不清楚，失败难定位 | 流式回复、步骤状态、局部重试、取消反馈、失败诊断 |
| P1 | 项目空间 | 多个相关任务无法长期共用资料和约定 | 项目目标、绑定知识库、默认团队/技能、任务列表与里程碑 |
| P1 | 成果中心 | 输出藏在聊天里，不易继续编辑 | Markdown/代码/表格预览、引用检查、版本差异和交付清单 |
| P1 | 全局搜索与上下文管理 | 不知道 AI 用了什么，也找不到旧工作 | 搜索任务、资料、Wiki、技能；查看本轮实际知识/技能/模型版本 |
| P1 | 使用量与任务预算 | 多成员协作容易产生不可见成本 | 分模型/成员用量、估算费用、调用/时长上限；未知费用明确标注 |
| P1 | 模板与成功任务复用 | 每次建队、配置和整理都从头开始 | 保存任务模板、复制团队、把成功流程转成技能草稿 |
| P1 | 备份、恢复与迁移 | 长期资料积累后不能承受丢失 | 项目备份、Wiki/技能导出、配置迁移；密钥单独处理 |
| P2 | 计划任务与变更触发 | 重复工作仍需手动启动 | 定时整理、目录变更触发；先支持应用运行时，明确离线行为 |
| P2 | 浏览器收集与应用连接 | 工作资料分散在网页和外部应用 | 网页收藏与摘录、少量高需求服务连接 |
| P2 | 在线技能市场和知识图谱 | 更广的分享与探索体验 | 在基本工作闭环可靠后再做 |

多用户组织、复杂企业管理和移动端暂不进入这一轮，保留个人工作台的定位。

## 6. 页面安排

主侧栏建议使用：**工作台、项目、Agent 与团队、知识库、技能库、工具与连接**。模型中心和设置保留在底部。Agent 与团队合并为一个入口下的两个页签。

工作台首页保留任务输入框，增加小型资源选择：执行团队、所属项目、知识库、技能。默认沿用项目配置，详细设置按需展开。

任务页保持已经调整好的大比例对话区，不再为新增功能压缩对话。右侧继续承担检查职责：

- 资料与成果：原始附件、检索引用、阶段文件、最终成果。
- 上下文：本轮知识库及版本、启用技能、记忆和模型选择。
- 执行：Leader 分工、成员状态、工具调用、等待用户处理的事项。

任务结束后，在成果附近提供“加入知识库”“保存为模板”“提炼为技能”。这些操作先生成可查看的草稿，避免把未验证的推断自动变成长期事实。

## 7. 如何接到现有代码

当前代码的具体限制：

- `src/core/storage.ts` 使用整体 JSON 快照，每次变更都会复制、写入和广播完整状态。
- `src/core/engine.ts` 将资料正文直接放入每轮上下文，并以 512 KB 作为总量保护；不能承载大规模知识库。
- `src/core/models.ts` 只有列出、读取、写入三个文件工具，缺少检索和技能激活接口。
- `src/core/external.ts` 的 Claude 适配明确使用空 MCP 配置，目前不能把知识工具直接提供给外部 Agent。
- `src/renderer/app.ts` 集中管理大量页面和事件，新增知识与技能模块前应按领域拆分，避免继续扩张单文件。

建议新增以下模块（规划名称）：

| 模块 | 职责 |
| --- | --- |
| KnowledgeService | 知识库、来源映射、同步、访问范围 |
| IngestionQueue | 可取消、可重试、有检查点的解析与整理任务 |
| DocumentParserRegistry | 按格式选择解析器及能力状态 |
| RetrievalService | 原文/Wiki 检索、排序和引用解析 |
| WikiCompiler | 主题整理、跨页更新、变更草稿与提交 |
| SkillRegistry | 扫描、校验、安装、版本、兼容性 |
| SkillStudio | 表单/源码编辑、AI 辅助创建和试运行 |
| CapabilityRegistry | 工具能力、依赖、权限与运行条件 |
| ContextAssembler | 为不同成员构建有限且可追溯的上下文 |
| ProjectService | 长期项目与任务、知识、技能的关联 |

初步数据对象：KnowledgeLibrary、SourceRevision、ParsedDocument、Citation、WikiPageRevision、IngestionJob、SkillPackage、SkillVersion、SkillBinding、Capability、Project，以及任务中的 ResourceSnapshot。

存储建议逐步升级为 SQLite 元数据/检索索引与文件正文组合。迁移前备份现有 state.json；迁移可重复执行，并保留回退路径。界面只接收摘要和增量事件，文件正文按需加载，避免整库广播。

建议增加的受控工具包括 knowledge_search、knowledge_read、knowledge_resolve_citation、wiki_propose_update、skill_activate。实际名称需在实现时统一；这些工具不能接受无约束的任意系统路径。目录读取范围由用户选择的知识库决定，Wiki 写入只允许进入该库的管理目录。

## 8. 推荐开发顺序

### 阶段 A：知识与技能可用（下一轮重点）

- 知识库入口、指定目录/文件导入、后台解析与全文检索。
- 原始资料与 Wiki 分层，最小主题整理、引用定位、版本与更新草稿。
- 技能三入口：手写、AI 辅助创建、精选预置包。
- 在 Agent/团队/任务中选择知识与技能，并记录实际使用情况。
- 本地知识工具、技能按需加载、基本 MCP 接口。
- 必要的存储与界面模块拆分，避免大文件影响主线程。

这阶段的验收必须包含一次真正的“目录资料 → Wiki → 团队使用知识与技能 → 带来源成果”任务，而不只是增加管理页面。

### 阶段 B：日常工作完整

- 项目空间、统一工具与连接管理、联网搜索、常见文档处理。
- 流式对话、任务预算、局部重试、成果编辑与差异。
- 持续同步、中文检索优化、可选向量检索和知识健康检查。
- 成功任务沉淀为知识、技能与模板；备份恢复。

### 阶段 C：主动运行与生态

- 计划任务、目录变更触发、网页收集、更多外部应用连接。
- 技能目录/市场、更多执行器适配、知识关系图与可选同步。

不在没有容量与使用数据时承诺具体工期。解析器、系统安全存储、外部 Agent 与后台常驻都要经过 Windows/macOS 验证。

## 9. 验收样例

1. 选择含中文文件名、嵌套目录、重复文件和不支持格式的资料目录，系统给出逐文件状态并保持界面可用。
2. 修改或移走一个来源，只处理受影响资料；暂时离线目录不被当成整库删除。
3. 对知识库提问，引用能打开对应版本的原文位置；找不到证据时明确表示不足。
4. 新资料与旧结论冲突时保留来源和更新差异，不覆盖人工修订。
5. 三种技能创建路径都能生成可用技能；缺工具的技能显示缺项，不能假装执行成功。
6. 一个技能升级后，进行中的任务仍使用固定版本；用户自定义版本不被覆盖。
7. 在一个混合团队中，让自建 Agent 与已接入 Agent 使用同一知识库；不兼容能力明确显示。
8. 将成果采纳到 Wiki，再在新任务中检索到；未采纳成果不能被当作已验证知识。
9. 导出 Wiki 与技能后可脱离 Forma 阅读；迁移和恢复后引用、批注、版本关系保持一致。

## 10. 建议先验证的一条完整故事

用户建立“产品研究”项目，选择已有资料目录，并拖入几份报告。Forma 解析文件，形成可搜索原文和带来源的主题 Wiki。用户选用自己的研究团队，启用“跨文档对比”和“研究报告”技能，只向 Leader 提出目标。Leader 检索证据、按职责分派成员，交付带引用的报告。用户修改并验收后，将可靠结论保存到 Wiki，将有效流程提炼成自己的技能。下一项工作直接复用这些积累。

这条故事同时检验知识、技能、工具、团队、成果和长期积累，适合作为丰富工作台的第一条验收主线。

## 11. 指定参考项目：nashsu/llm_wiki

### 已核对的事实

该项目使用 Tauri/Rust 桌面架构，公开说明包含增量入库、来源追溯、目录导入与监听、原文/Wiki 检索、可选向量检索、技能和成果预览。它与 Forma 的 Electron 架构不同，需要通过清晰的适配边界整合。来源：[项目说明](https://github.com/nashsu/llm_wiki)、[前端依赖](https://github.com/nashsu/llm_wiki/blob/main/package.json)。

MCP 包调用运行中桌面应用的本地 HTTP API；它本身不扫描目录，也不包含独立的检索引擎。公开工具包括状态、项目、文件读取、检索、聊天、关系图和来源重扫。来源：[MCP 说明](https://github.com/nashsu/llm_wiki/blob/main/mcp-server/README.md)。

上游 LICENSE 为 GPLv3，Forma 目前为 MIT。直接复用或改造上游代码时必须评估相应的许可与分发义务，不能把复制后的代码全部标为 MIT。进程分离或 API 调用也不能被简单当成任何情形下的许可豁免。来源：[上游许可证](https://github.com/nashsu/llm_wiki/blob/main/LICENSE)。本轮未引入上游代码，也未变更 Forma 许可证。

### 三条集成路线的取舍

| 路线 | 用户体验 | 工作量与约束 | 建议 |
| --- | --- | --- | --- |
| Forma 原生知识库，独立实现所需能力 | 安装 Forma 后直接选目录或导入文件 | 需要实现解析、增量整理、检索和引用；可逐步交付 | 作为产品默认路径 |
| 连接用户已有 llm_wiki | 复用其现有项目和检索结果 | 需要上游桌面程序运行并开启 API/MCP；接口版本要验证 | 作为可选连接器 |
| 提取/改造上游引擎，作为随包组件 | 有机会提供单应用体验 | 要验证 Rust 模块与 Tauri 的耦合、无头运行、生命周期、打包及许可；不能把现有 MCP 包当成独立引擎 | 单独做技术验证后再决定 |

建议先采用前两条路线。它们服务于不同用户：新用户直接使用 Forma 内置知识库，已有 llm_wiki 用户可以连接自己的资料。连接器完成不代表“内置知识库”完成。

### 用户可见的知识库来源

“新建知识库”提供：

1. **从目录建立**：选择来源目录、整理主题和模型，生成 Forma 管理的知识库。
2. **从文件建立**：拖入文件或选择文件，归入托管来源。
3. **连接 LLM Wiki**：检测/填写本机连接、配置访问令牌、选择指定项目、测试检索。

三者统一呈现资料、Wiki、检索、引用和可用状态。外部连接不伪装成本地托管资料：上游未运行、权限关闭或项目不可用时，准确显示原因。

### 可选连接器的第一版边界

- 先做状态、项目选择、检索、文件读取和引用定位，采用用户配置的令牌，不要求关闭上游认证。
- 每个任务绑定明确的项目 ID。根据上游项目固定机制建立会话，不能跟随用户在上游界面切换“当前项目”而悄悄改变检索范围。
- 将外部结果转换为 Forma 自己的证据结构，记录来源连接、项目、文件与可获得的版本信息。拿不到稳定版本时明确标记，不伪造版本号。
- 来源重扫是有副作用的操作，可能触发入库和模型消耗，应作为单独的用户操作或明确启用的策略。
- 初版不默认调用上游聊天工具参与每一次检索。优先由 Forma Leader 使用检索证据回答，避免两套 Agent 循环带来的重复费用和不透明上下文。
- 公开 MCP 工具清单不能证明任意文件上传、Wiki 编辑和完整深度研究都已开放。缺少的接口保留为待验证能力，不通过绕写上游内部状态文件实现。
- 不把令牌写入命令行、技能包或导出配置；连接信息和凭据沿用 Forma 的安全存储与作用域管理。

### 从参考项目转化为 Forma 的产品要求

以下为 Forma 的设计建议：

- 知识库除名称外，应有“研究目标/范围”和“整理规则”，帮助用户长期维护同一主题。
- 大批资料使用后台队列，显示进度、失败项与重试范围；同一知识库的页面提交应协调写入。
- 入库先生成可检查的结构化提要和更新计划，再生成页面；界面展示事实、来源和变更摘要，不要求展示模型内部思维。
- 提供“仅依据原始资料”和“结合整理后的知识”两种回答范围，方便用户核查。
- 引用回溯、增量更新、冲突待办、技能调用和成果沉淀先于复杂图谱可视化。

### 下一步的最小技术验证

独立验证一条原生路径和一条连接路径：

- 原生：选择一个小型中英文资料目录 → 解析与检索 → 生成可审阅 Wiki → 团队输出带引用的报告。
- 连接：上游运行并授权 → 选择固定项目 → 搜索与读取 → Leader 引用；再验证上游关闭、项目切换、令牌失效等情况。

技术验证结果应记录支持版本与能力矩阵，再决定是否扩大代码复用范围。

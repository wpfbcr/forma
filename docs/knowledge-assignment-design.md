# 知识库如何分配给团队与 Agent

状态：产品与实现规划；不能视为当前 0.2 已实现的完整权限机制。

## 1. 产品定位

知识库是用户管理的独立资料资产。Agent 或团队获得知识库的使用配置后，才能在执行任务时检索其中的资料。一个知识库可以供多个 Agent、多个团队复用，建立绑定不会复制整个资料库。

知识库中心负责接入、整理、检索、来源和版本；Agent 与团队页面负责决定“谁在工作中使用这些知识”。知识库仍可由用户直接浏览和问答，但主要价值应体现在任务交付中。

## 2. 三层分配

### Agent 自带知识

在 Agent 配置中增加独立的“知识”页签。用户选择该 Agent 长期使用的知识库，可限定库内文件夹、标签或资料集合，并写下使用说明。

例如：“品牌写作助手”绑定品牌规范和历史文章，“开发助手”绑定技术文档和项目约定。Agent 独立运行时使用这些配置。

加入团队时，在成员配置里明确展示“继承 Agent 自带知识”。默认继承，可针对这个团队关闭或排除某个库，避免改动全局 Agent。该配置只影响当前团队。

### 团队知识

在团队配置中增加“共享知识”页签。每个绑定可以选择三种范围：

| 使用范围 | 效果 |
| --- | --- |
| 全体成员（默认） | Leader 和执行成员均可检索，适合团队公共资料 |
| 仅 Leader | Leader 用于理解目标与规划，不直接提供给成员检索 |
| 指定成员 | 只开放给选中的成员，可选是否包含 Leader |

公共要求、项目背景和交付规范适合团队级绑定；专业资料适合分配给具体成员。Leader 本身也是一个 Agent，使用其自带知识和明确分配给它的团队资料。

### 本次任务临时资料

开始任务时允许增加知识库或上传资料，并选择接收范围。团队任务默认全体成员，用户可改为 Leader 或指定成员；单 Agent 任务默认分给当前 Agent。

任务中的临时选择不自动改变 Agent 和团队的长期配置。执行中调整作为下一轮的资源变更，明确显示生效范围；当前轮使用启动时的快照。

## 3. 有效范围的计算

对每个团队成员分别计算：

```text
有效知识范围 =
  本团队允许继承的 Agent 自带知识
  + 分配给该成员的团队知识
  + 本轮临时分配给该成员的知识
  - 当前团队或任务明确排除的范围
```

同一知识库去重；库内范围限制同时生效，不能因为去重而扩大访问范围。不同对象的排除和新增存在冲突时，以当前任务界面显示的最终有效范围为准，并提供来源说明。

用户在开始任务前可以展开“成员实际可用知识”，看到每个库来自 Agent、团队还是临时资料。运行时必须使用同一份解析结果，不能仅在界面上显示限制。

绑定只赋予应用内部的检索能力，不自动改变外部 Agent 的操作系统权限，也不把原始目录以任意文件路径形式开放给模型。

## 4. Leader 怎样组织使用

1. Leader 使用自己可用的资料理解目标、形成分工。
2. 分派某项任务时，根据成员职责生成具体的问题与检索意图。
3. 为成员解析有效知识范围，用该成员的问题检索相关内容。
4. 成员收到自己的任务、必要证据与依赖结果，按需继续检索。
5. 成员向 Leader 提交结论、引用、证据不足或冲突说明。
6. Leader 整合交付，保留证据来源；需要进一步核查时重新派发给对应成员。

Leader 不应为了协调而自动收到所有成员知识库的全部检索正文。默认可以接收成员为当前任务提交的摘要与引用；知识的使用范围和成员汇报范围需要分别表达。更严格的资料隔离场景应显式限制汇报内容，不能把单人角色配置宣传成企业级保密机制。

用户始终只与 Leader 对话，不需要分别打开每位成员的聊天。

## 5. 举例：内容研究团队

| 对象 | 自带知识 | 团队分配 | 实际工作 |
| --- | --- | --- | --- |
| Leader | 工作方法与验收约定 | 研究目标、客户要求 | 规划、协调、验收 |
| 研究员 | 行业研究资料 | 研究目标、客户要求、竞品资料 | 检索并整理有依据的结论 |
| 写作者 | 品牌规范、历史文章 | 研究目标、客户要求 | 使用研究员提交的证据形成稿件 |
| 审阅员 | 事实核查规则 | 研究目标、客户要求、竞品资料 | 核对结论、引用和交付要求 |

“研究目标与客户要求”绑定到全体；“竞品资料”只绑定研究员和审阅员。写作者可使用研究员交付的摘要与引用，无须接收整套研究原文。

## 6. 配置界面

### 从知识库分配

知识库详情增加“分配使用”按钮：选择 Agent 或团队 → 选择范围 → 设置只读/可提议更新 → 保存。详情页显示“哪些 Agent 和团队正在使用”，支持跳转和解除绑定。

### 从 Agent 配置

基本信息、模型、工具、技能之外，单独呈现“知识”：知识库名称、资料范围、使用说明、状态和版本。按钮为“添加知识库”，支持选择已有库或新建后返回当前配置。

### 从团队配置

团队级共享知识和成员级专属知识分别呈现。画布节点展示简短数量标记，点击后在侧栏显示：

- Agent 自带且已继承的知识。
- 团队分配给此成员的知识。
- 本团队关闭的继承项。

同一侧栏可以预览最终有效范围，避免用户在多个页面间反复计算。

### 在任务中检查

任务页顶部保持轻量的知识数量入口；右侧“上下文”显示本轮的资源版本、各成员可用范围与实际检索记录。点击引用打开对应证据，不占用主要对话区域。

## 7. 使用与维护分开

默认 Agent 与团队只读使用知识。执行成员可以提交知识更新建议，不能直接改原始资料或覆盖 Wiki。

知识库整理模型/维护 Agent 由用户单独选择，用于入库和整理草稿，不自动成为所有业务团队的 Leader。用户采纳变更后再更新 Wiki；允许自动整理的库也应有明确的提交范围和记录。

只读、提议更新、管理导入和删除应是不同操作。技能不能改变这些范围。

## 8. 检索与版本策略

绑定表达可使用的知识范围；实际执行只加载相关内容。先披露知识库用途和检索入口，再根据当前分派查询原文或 Wiki，不把整个知识库一次性写入提示词。

每轮记录：绑定配置版本、成员范围、查询、引用的来源版本、结果片段以及实际使用的技能。知识更新后，新轮次读取新版本，历史任务仍可解释其当时依据。

为了恢复历史依据，保留证据片段或必要的来源版本副本，不仅保存无法重现的文件名。库被移走、断开或处理失败时，界面明确显示状态；不无提示地扩大检索到其他库。

## 9. 对当前实现的修正

0.2 已有 Agent、团队、任务的 knowledgeIds 绑定。当前规则主要是团队/任务知识与个人知识的合并，所有成员按同一个任务问题预检索；这属于基础绑定，尚不具备上述精细分配。

需要修改：

1. 将单纯 knowledgeIds 升级为包含目标范围、库内过滤和使用模式的 KnowledgeBinding。
2. 增加团队成员的继承开关和排除项，统一计算 EffectiveKnowledgeScope。
3. 检索从“所有成员用同一任务问题”改为“按分派任务检索”；规划阶段和执行阶段分别构建上下文。
4. Leader 的提示词不再包含其他成员完整的资源快照，只保留其可用资料和协作所需能力说明。
5. 增加受限的 knowledge_search/read 接口，每次校验成员、任务和有效范围，记录来源引用。
6. 任务快照继续完整归档，但归档记录不等于每个 Agent 都可以读取其中全部内容。
7. 旧绑定迁移为等价默认：Agent 绑定转为自身知识；团队绑定转为全体共享；任务绑定转为本任务全体共享。

## 10. 验收重点

- 一个库同时分给两个团队，无需复制资料。
- Agent 独立运行、加入团队、关闭继承时使用的范围都符合界面配置。
- “仅 Leader”和“指定成员”的资料不会出现在其他成员的实际请求中。
- 成员检索使用自身分派问题，而非机械复用用户最初的总目标。
- 配置变更不静默改变当前轮，下一轮的实际快照与界面一致。
- 成员输出保留引用，Leader 可以通过对应成员核查证据。
- 读取权限不能被技能内容或模型构造的任意库 ID 绕过。
